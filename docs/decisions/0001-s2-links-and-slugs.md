# ADR-0001 : S2 account, token and link implementation choices

- **Date** : 2026-11-21

## Context

`docs/07-schema.md`, `docs/10-api.md` and `docs/12-uml.md` fix the account,
token and link contract, but several storage details were left open. S2 must
implement them without adding a public endpoint or changing a frozen decision.
The constraints are: no email in clear text outside the encryption boundary, a
closed failure when Valkey is unavailable, replay detection for refresh tokens
and TOTP, and a public API that never exposes an internal hash.

## Decision

- **Password reset tokens live in Valkey only.** Key
  `password-reset:{public_id}`, value the SHA-256 of the random secret, TTL one
  hour, deleted on use. The Laravel `password_reset_tokens` table is dropped: it
  would store an email in clear text. A Valkey failure answers `503`
  `server_error`; a reset that succeeds revokes every refresh family.
- **TOTP replay protection lives in Valkey.** Key `totp:{public_id}`, value the
  last accepted timestamp, TTL 120 seconds, written with
  `Google2FA::verifyKeyNewer()`. A Valkey failure answers `503`; a Valkey
  outage therefore blocks 2FA logins.
- **Refresh replay is detected with `personal_access_tokens.consumed_at`.** A
  consumed refresh row keeps its original `expires_at`, so a replay still
  identifies its `family_id` and revokes the whole family. The row is removed
  by `sanctum:prune-expired` at its normal expiry. Rotation takes a
  transaction-scoped PostgreSQL advisory lock on the family before locking the
  token row, then creates the replacement tokens in the same transaction; a
  request losing the race revokes the family and answers 401. The family lock
  prevents two replays of different tokens in one family from deadlocking on
  each other's row locks.
- **TOTP replay and password-reset consumption are serialised with a Valkey
  lock.** Two concurrent requests cannot both accept the same TOTP step or the
  same reset token. A lock or cache failure is a closed `503`, and the password
  update and refresh revocation share one database transaction. Disabling 2FA
  does not clear the replay key: a concurrent request already holding the old
  secret must still see the consumed step, and the 120-second TTL is the
  bounded cleanup.
- **`me:write` is a dashboard-only ability.** It covers `PATCH /me/password`,
  `DELETE /me`, `POST /auth/logout-all` and the 2FA mutations. `POST /tokens`
  refuses `me:write` and `*`; the allowed API scopes are `me:read`,
  `links:read`, `links:write`, `stats:read`, `tokens:read` and `tokens:write`.
  A non-`*` token may only mint a subset of its own abilities.
- **Auth emails are sent synchronously**, never queued, so a failed delivery
  cannot leave a clear email address in `failed_jobs`. A failure logs only the
  user's `public_id`.
- **The capability list describes the plan**, never the current token:
  `links:read`, `links:write`, `stats:read`, `tokens:read`, `tokens:write`,
  `qr`. Scopes and capabilities are different concepts.
- **Slug generation uses the 33-character lowercase alphabet** from D-135.
  Generated collisions are retried on the unique constraint; custom slugs are
  normalised to lowercase before every check.
- **The OpenAPI document is committed** as `openapi.json`, generated by
  `scramble:export --fail-on-unknown`. `/docs` and `/openapi.json` are public;
  the legacy `/docs/api` path is kept because an S1 test asserts it.

## Consequences

- **Positive**: no clear email leaves the encryption boundary; replay is
  detected for the full refresh lifetime; 2FA and password reset fail closed.
- **Negative**: a Valkey outage blocks 2FA logins and password resets. The
  consumed refresh row stays in the table until its original expiry. A
  concurrent double-submit is treated as a replay and revokes the refresh
  family, by design.
- **Trade-offs**: synchronous mail adds provider latency to registration and
  password-reset requests, in exchange for keeping addresses out of the queue
  payloads.

## Rejected alternatives

- **Laravel Fortify**: its HTTP layer is session/CSRF/redirect based, its 2FA
  challenge lives in the session, its 2FA columns are `two_factor_secret` and
  `two_factor_recovery_codes`, and its password broker stores the email in
  clear in `password_reset_tokens`. Adopting it would require rewriting its
  session guard, its 2FA storage, its reset broker and its responses, which is
  more coupling than the explicit actions used here. It is incompatible with
  D-114, `docs/07` and `docs/10` as written.
- **Laravel password broker with `password_reset_tokens`**: stores the email in
  clear text and is not compatible with the encrypted column.
- **A dedicated reset table**: adds a table absent from `docs/07`; the cache
  already provides the one-hour, single-use semantics.
- **Marking a consumed refresh in `abilities`**: overloads a column whose
  meaning is the token's scopes. `consumed_at` is explicit and queryable.
- **Queued auth emails**: a failed job would persist the recipient address.
- **Per-operation OpenAPI `security` only**: Scramble emits a document-level
  scheme and explicit `security: []` on public operations; that is a valid
  OpenAPI 3.1 representation of the same contract.
